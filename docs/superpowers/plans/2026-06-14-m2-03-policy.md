### Seam 4: Whitelist semantics — `AllowedTools` is "allow ONLY these"

The master doc implies (and acceptance #1/#2 require) that a delegate agent ends up with exactly the five read-only tools. **This is enforced by the coordinator's filter** (`internal/agent/coordinator.go:554-575`):

```go
var filteredTools []fantasy.AgentTool
for _, tool := range allTools {
    toolName := tool.Info().Name
    // Layer 1: agent whitelist (existing behavior).
    if !slices.Contains(agent.AllowedTools, toolName) {
        continue
    }
    // Layer 2 (M1-02): sub-agent safety filter. ...
}
```

A tool NOT in `AllowedTools` is skipped (`continue`). So a delegate with `AllowedTools = [view, grep, glob, ls, sourcegraph]` gets exactly those five (after the M1-02 sub-agent denylist also strips any that overlap). The read-only policy is therefore load-bearing on Layer 1, not just Layer 2.

**Important boundary:** `coordinator.go:559` reads `agent.AllowedTools` off a `config.Agent` struct (the coder/sub-agent config), NOT off `agent.ToolPolicyProfile`. `ToolPolicyProfile` is the descriptor carried by `TeamAgentCall`/`AgentSpec` (M1-04 seam, `team_call.go:37,74`); the production `AgentFactory` (not yet shipped — M2-01 Seam 2) is the code that will map `spec.ToolPolicy.AllowedTools` → `config.Agent.AllowedTools` before building the runner. M2-03 only defines the policy literal; the factory wiring that actually applies it is the deferred production-factory task. The plan states this boundary explicitly so the team-lead review does not mistake M2-03 for "delegates are now sandboxed end-to-end" — they are not until the production factory lands. **Evidence:** `internal/agent/coordinator.go:554-575`; M2-01 plan Seam 2 (`docs/superpowers/plans/2026-06-14-m2-01-delegate-runner.md:37-46`).

### Seam 5: Decision — SWITCH M2-01's in-package helper onto the exported function (no duplicate)

This is the load-bearing design decision for M2-03. Two options were considered:

**Option A (recommended, chosen): SWITCH.** Export `agent.ReadOnlyDelegatePolicy()` in `internal/agent/team_call.go`, then change M2-01's `delegateReadOnlyPolicy()` (in `internal/team/delegate_types.go:131-142`) to be a one-line alias `return agent.ReadOnlyDelegatePolicy()`, OR delete it entirely and update its two call sites (`delegate_runner.go:82`, `delegate_types_test.go:94`) to call `agent.ReadOnlyDelegatePolicy()` directly.

**Option B (rejected): ADD only, keep both.** Export `agent.ReadOnlyDelegatePolicy()` for M2-04 UI / future consumers, but leave M2-01's `delegateReadOnlyPolicy()` untouched (the delegate runner keeps calling its own copy).

**Why Option A (SWITCH):**

1. **No duplicate policy literals.** Option B leaves two identical 14-line `ToolPolicyProfile{...}` literals in the tree. A future policy tweak (e.g. allow `web_fetch`) would have to be made in both places, and one would inevitably drift — a real correctness hazard for a security-relevant allowlist. The M2-01 plan itself flagged this risk and explicitly pre-approved the switch (Seam 3, `2026-06-14-m2-01-delegate-runner.md:52-57`: "if M2-03 later exports the agent-level function, M2-01's delegateRunner can be switched to call it in a one-line change").

2. **No cycle / no layering violation.** `internal/agent` does NOT import `internal/team` (verified: `grep '"github.com/charmbracelet/crush/internal/team"' internal/agent/` returns zero matches). `internal/team` already imports `internal/agent` (`delegate_types.go:14`). So `team → agent.ReadOnlyDelegatePolicy` is a clean one-directional dependency. There is no import cycle risk.

3. **Minimal blast radius.** The switch touches M2-01 code in only two places (`delegate_runner.go:82` call, `delegate_types_test.go:94` call) plus the deletion of the 21-line `delegateReadOnlyPolicy()` helper. The `team` package already imports `agent`, so no new import is added. M2-01's acceptance criteria (parallel dispatch, panic recover, Results fill, in-memory) are all behavioral and untouched by a policy-literal relocation.

**Concrete decision within Option A — delete vs alias:** The plan **deletes** `delegateReadOnlyPolicy()` entirely and points both call sites at `agent.ReadOnlyDelegatePolicy()`. Rationale: an alias `func delegateReadOnlyPolicy() agent.ToolPolicyProfile { return agent.ReadOnlyDelegatePolicy() }` would preserve the indirection for zero benefit (the call sites already live in package `team` and can call the exported function directly). Deleting is the cleaner consolidation and is what "one definition in the codebase" means. The existing M2-01 test `TestDelegateReadOnlyPolicy_Shape` is renamed to `TestReadOnlyDelegatePolicy_Shape` and migrated to assert the exported function's shape (so the shape stays locked at the `agent` level, where M2-04 UI will consume it).

**Evidence the switch is mechanically safe:** `delegateReadOnlyPolicy()` returns `agent.ToolPolicyProfile{...}` with exactly the same five-tool allowlist and 14-tool disallow list the master doc specifies (`03-m2-delegate-runner.md:413-419`). The exported `agent.ReadOnlyDelegatePolicy()` returns the identical literal. The two call sites consume only the returned struct value; neither inspects which function produced it. **Evidence:** `internal/team/delegate_types.go:122-142`, `internal/team/delegate_runner.go:82` (`policy := delegateReadOnlyPolicy()`), `internal/team/delegate_types_test.go:93-106`, `internal/agent/team_call.go:40-45`.

// TestReadOnlyDelegatePolicy_Shape locks acceptance #1 and #2 from the master
// task doc (03-m2-delegate-runner.md:427-428): the delegate read-only policy
// allows exactly the five read-only tools and disallows the destructive ones.

	assert.Equal(t, "default", p.PermissionMode)

	// Allowlist: exactly the five read-only tools (order-independent).
	assert.ElementsMatch(t,
		[]string{"view", "grep", "glob", "ls", "sourcegraph"},
		p.AllowedTools,
		"delegate allowlist must be exactly the five read-only tools")

	// Destructive tools must be in the disallow list. The load-bearing ones
	// (acceptance #2): bash/write/edit/agent must never be reachable.
	for _, banned := range []string{"bash", "write", "edit", "agent"} {
		assert.Contains(t, p.DisallowedTools, banned,
			"destructive tool %q must be in the disallow list", banned)
	}
}

// TestReadOnlyDelegatePolicy_AllowAndDisallowDisjoint locks a consistency
// invariant: no tool appears in both AllowedTools and DisallowedTools. A tool
// in both would be a contradiction (allowed by Layer 1 of the coordinator
// filter, then stripped by Layer 2 — confusing and a sign of a copy-paste bug).
func TestReadOnlyDelegatePolicy_AllowAndDisallowDisjoint(t *testing.T) {
	p := ReadOnlyDelegatePolicy()

	allowed := map[string]bool{}
	for _, a := range p.AllowedTools {
		allowed[a] = true
	}
	for _, d := range p.DisallowedTools {
		assert.False(t, allowed[d],
			"tool %q appears in BOTH AllowedTools and DisallowedTools — contradiction", d)
	}
}

// TestReadOnlyDelegatePolicy_NoSharedMutableState locks that the function is a
// pure literal: every call returns a fresh, independent value. A caller must
// not be able to mutate one delegate's policy and affect another's. This guards
// against a future "optimization" that returns a package-level var by reference.
func TestReadOnlyDelegatePolicy_NoSharedMutableState(t *testing.T) {
	p1 := ReadOnlyDelegatePolicy()
	p2 := ReadOnlyDelegatePolicy()

	// Mutate p1's allowlist.
	p1.AllowedTools[0] = "MUTATED"

	// p2 must be unaffected.
	assert.NotContains(t, p2.AllowedTools, "MUTATED",
		"ReadOnlyDelegatePolicy returned shared mutable state — calls are not independent")
	assert.Equal(t, "view", p2.AllowedTools[0],
		"mutating one policy's allowlist corrupted another call's result")
}

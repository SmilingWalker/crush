# M4-03 Scheduler: ClaimNextTask + Heartbeat + Stale Recovery

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `Scheduler` to `package team` that coordinates task claiming (delegate to Service's atomic `ClaimNextTask`), per-run heartbeat goroutines (periodic `HeartbeatRun` tickers), and startup stale-run recovery (detect runs whose heartbeat expired, mark them `interrupted`). The Scheduler wraps `team.Service` — it adds goroutine lifecycle and recovery orchestration, but delegates ALL database operations to Service.

**Architecture:** Two new files + one Service-interface expansion. (1) `internal/team/recovery.go` defines `StaleRunInfo` and `RecoveryReport` types shared between M4-03 (basic stale detection) and M4-08 (expanded recovery). (2) `internal/team/scheduler.go` defines `SchedulerConfig`, the `Scheduler` struct, `NewScheduler`, and three methods: `ClaimNextTask` (thin delegation), `StartHeartbeat` (goroutine + ticker + cancel func), `RecoverStaleRuns` (cutoff → `FindStaleRuns` → `MarkRunTerminal` for each). (3) The Service interface gains `FindStaleRuns` (surfaces the existing RunStore method, which the teamService already calls internally in `findRunsForSnapshot`). (4) `internal/team/scheduler_test.go` covers all acceptance criteria.

**Tech Stack:** Go 1.26.3 (`module github.com/charmbracelet/crush`), `github.com/stretchr/testify` (assert + require), in-memory SQLite fixture via `newServiceFixture` (same package `team`, no import barrier). ## Design seam corrections (vs master task doc M4-03:382-456)

### Seam 1: Scheduler wraps `team.Service` only — no raw `*sql.DB`

The master doc snippet (`:400-404`) shows `Scheduler{db *sql.DB, svc TeamService, cfg SchedulerConfig}`. **Decision:** hold only `svc TeamService` + `cfg SchedulerConfig`. The Service already owns `*sql.DB` and all 6 stores; adding a raw DB handle to Scheduler invites bypassing the Service's tx lifecycle. **Evidence:** `internal/team/service.go:151-158` (teamService holds `db` + 6 stores, each Service method owns its own `BeginTx`/defer-`Rollback`/`Commit`).

### Seam 2: `ClaimNextTask` is thin delegation — no member wake logic

The master doc code (`:407-413`) delegates to `svc.ClaimNextTask`. The Scheduler does NOT wake members — that's the caller's responsibility (M4-02 TeamRunner). **Evidence:** `internal/team/service.go:548-565` (Service.ClaimNextTask with atomic SQL CTE), `internal/team/member_runner.go:137-144` (Wake method for waking members).

### Seam 3: `StartHeartbeat` returns cancel func, accepts parent context

The master doc (`:416-431`) creates a child context and returns its cancel function. The caller provides the parent context for lifetime scoping. **Evidence:** `internal/team/service.go:634-647` (HeartbeatRun: BeginTx + UpdateRunHeartbeat + Commit).

### Seam 4: `RecoverStaleRuns` iterates stale runs, marks each via Service

The master doc (`:434-443`) calls `svc.FindStaleRuns` then marks interrupted. The Service's `FindStaleRuns` returns runs where `status IN ('running','waiting_permission','queued') AND heartbeat_at < cutoff`. Each stale run is marked via `svc.MarkRunTerminal` with `RunInterrupted`. **Evidence:** `internal/db/sql/team_queries.sql:75-78` (FindStaleRuns filter), `internal/team/service.go:664-677` (MarkRunTerminal).

### Seam 5: `RecoveryReport` + `StaleRunInfo` in `recovery.go` (shared M4-03/M4-08)

The master task doc lists both `scheduler.go` and `recovery.go` as M4-03 outputs; M4-08 modifies `recovery.go` to add `InterruptedReason` + `UsageStatus` + member-state recovery. **Decision:** `recovery.go` holds the types only. `RecoverStaleRuns` lives on `Scheduler` in `scheduler.go`. M4-08 can add fields to `StaleRunInfo` without touching `scheduler.go`.

### Seam 6: `SchedulerConfig` defaults match master doc exactly

`HeartbeatInterval=30s`, `HeartbeatTimeout=90s`, `MaxConcurrentRuns=3`. `DefaultSchedulerConfig()` returns these. Tests override via struct literal for fast tickers. **Evidence:** master doc `:394-398`.

### Seam 7: `MaxConcurrentRuns` stored but NOT enforced in M4-03

The field is present (default 3) but enforcement logic belongs to M4-02 (TeamRunner), which holds the member registry and counts active runs per member. M4-03 stores the config value only.

### Seam 8: Concurrent claim test follows M3-04's 10-goroutine pattern

`TestTaskStore_ClaimNextTask_SingleWinnerUnder10Goroutines` (`store_task_test.go:103-164`) uses `SetMaxOpenConns(1)` to serialize DB access. M4-03's concurrent test uses the same pattern through the Scheduler (not raw `*sql.DB.BeginTx`). **Evidence:** `store_task_test.go:103-164`, `store_test_helpers.go:31` (SetMaxOpenConns(1)).

### Seam 9: Add `FindStaleRuns` to the Service interface (surfacing existing RunStore method)

`FindStaleRuns` exists on `RunStore` (`store_run.go:18`) and is called internally by `teamService.findRunsForSnapshot` (`service.go:304`), but it is NOT on the `Service` interface (`service.go:124-147`). `RecoverStaleRuns` needs it. **Decision:** add `FindStaleRuns(ctx context.Context, cutoff time.Time) ([]TeamRun, error)` to the Service interface, implemented as a one-line delegation to `s.runs.FindStaleRuns`. This is a 1-line interface addition + 10-line method body (enabledGuard + BeginTx + delegate + Commit). **Evidence:** `store_run.go:18` (RunStore.FindStaleRuns), `service.go:303-315` (existing internal caller), `service.go:124-147` (Service interface — FindStaleRuns absent).

### Seam 10: `MarkRunTerminal` guards on `status='running'` — stale `queued`/`waiting_permission` runs won't be marked

The SQL query (`team_queries.sql:70-73`) has `WHERE status = ?`, and `store_run.go:83` passes `string(RunRunning)` as the guard. `FindStaleRuns` returns runs with `status IN ('running','waiting_permission','queued')`, so stale runs in `queued` or `waiting_permission` would fail to be marked (the UPDATE matches zero rows). In practice, `queued` runs are transient (StartRun immediately flips to `running`), and `waiting_permission` runs belong to M5. M4-08 widens the guard. For M4-03, only stale `running` runs are recoverable — the test creates only `running` runs. **Evidence:** `store_run.go:83` (hardcoded `RunRunning` guard), `team_queries.sql:73`.

```go
// FindStaleRuns returns runs whose heartbeat_at is before cutoff AND status is
// in ('running','waiting_permission','queued'). Surfaced from RunStore to the
// Service interface for M4-03's RecoverStaleRuns (Seam 9).
func (s *teamService) FindStaleRuns(ctx context.Context, cutoff time.Time) ([]TeamRun, error) {
	if err := s.enabledGuard(); err != nil {
		return nil, err
	}
	tx, err := s.db.BeginTx(ctx, nil)
	if err != nil {
		return nil, fmt.Errorf("begin tx: %w", err)
	}
	defer func() { _ = tx.Rollback() }()
	runs, err := s.runs.FindStaleRuns(ctx, tx, cutoff)
	if err != nil {
		return nil, err
	}
	if err := tx.Commit(); err != nil {
		return nil, fmt.Errorf("commit: %w", err)
	}
	return runs, nil
}
```

```go
// scheduler.go implements M4-03 Scheduler: task claiming (delegating to
// Service's atomic ClaimNextTask), per-run heartbeat goroutines (periodic
// HeartbeatRun ticker), and startup stale-run recovery (detect runs whose
// heartbeat expired, mark them interrupted).
//
// The Scheduler wraps team.Service — it adds goroutine lifecycle and recovery
// orchestration, but delegates ALL database operations to Service.

package team

import (
	"context"
	"time"
)

// SchedulerConfig holds the tunable parameters for the Scheduler.
// Defaults from master doc M4-03:394-398.
type SchedulerConfig struct {
	HeartbeatInterval time.Duration // between heartbeat pings (default 30s)
	HeartbeatTimeout  time.Duration // stale threshold (default 90s)
	MaxConcurrentRuns int           // per-member limit (default 3, enforced by M4-02)
}

// DefaultSchedulerConfig returns the master-doc defaults.
func DefaultSchedulerConfig() SchedulerConfig {
	return SchedulerConfig{
		HeartbeatInterval: 30 * time.Second,
		HeartbeatTimeout:  90 * time.Second,
		MaxConcurrentRuns: 3,
	}
}

// Scheduler coordinates task claiming, heartbeat goroutines, and stale-run
// recovery. It wraps team.Service — all DB operations go through Service.
type Scheduler struct {
	svc Service
	cfg SchedulerConfig
}

// NewScheduler creates a Scheduler backed by the given Service.
func NewScheduler(svc Service, cfg SchedulerConfig) *Scheduler {
	return &Scheduler{svc: svc, cfg: cfg}
}

// ClaimNextTask delegates to the Service's atomic ClaimNextTask.
// The caller (M4-02 TeamRunner) is responsible for waking the member after a
// successful claim — the Scheduler only returns the claimed task.
func (s *Scheduler) ClaimNextTask(ctx context.Context, req ClaimNextTaskRequest) (TeamTask, error) {
	return s.svc.ClaimNextTask(ctx, req)
}
```

```go
// StartHeartbeat launches a background goroutine that calls HeartbeatRun on the
// Service every cfg.HeartbeatInterval. The parent context controls lifetime:
// when it is cancelled, the goroutine stops. The returned cancel function lets
// the caller stop the heartbeat explicitly (e.g. after FinishRun or
// MarkRunTerminal).
//
// Heartbeat failures are non-fatal — the goroutine logs nothing in M4-03.
// M4-08 adds error logging and retry.
func (s *Scheduler) StartHeartbeat(ctx context.Context, runID string) (func(), error) {
	ctx, cancel := context.WithCancel(ctx)
	go func() {
		ticker := time.NewTicker(s.cfg.HeartbeatInterval)
		defer ticker.Stop()
		for {
			select {
			case <-ctx.Done():
				return
			case <-ticker.C:
				if err := s.svc.HeartbeatRun(ctx, runID); err != nil {
					// Non-fatal: M4-08 adds logging/retry here.
				}
			}
		}
	}()
	return cancel, nil
}
```

```go
// RecoverStaleRuns finds runs whose heartbeat_at is older than
// cfg.HeartbeatTimeout from now, marks each as interrupted via
// MarkRunTerminal, and returns a RecoveryReport. Only runs with status IN
// ('running','waiting_permission','queued') are returned by FindStaleRuns;
// MarkRunTerminal's status guard ('running') means only stale runs in
// 'running' are successfully marked (Seam 10 — M4-08 widens this).
//
// Idempotent: once a run is marked interrupted, it no longer matches the
// FindStaleRuns status filter, so a second recovery pass finds zero stale
// runs (unless new runs became stale in the meantime).
func (s *Scheduler) RecoverStaleRuns(ctx context.Context) (*RecoveryReport, error) {
	cutoff := time.Now().Add(-s.cfg.HeartbeatTimeout)
	stale, err := s.svc.FindStaleRuns(ctx, cutoff)
	if err != nil {
		return nil, err
	}

	report := &RecoveryReport{}
	for _, run := range stale {
		info := StaleRunInfo{
			RunID:    run.ID,
			TeamID:   run.TeamID,
			MemberID: run.MemberID,
			Status:   string(run.Status),
		}
		if run.HeartbeatAt != nil {
			info.LastHeartbeat = *run.HeartbeatAt
		}

		// MarkRunTerminal guards on status='running' (Seam 10). A stale run in
		// 'queued' or 'waiting_permission' will fail to match — skip it silently.
		// M4-08 widens the guard to accept those statuses too.
		if err := s.svc.MarkRunTerminal(ctx, MarkRunTerminalRequest{
			TeamID: run.TeamID,
			RunID:  run.ID,
			Status: RunInterrupted,
			Error:  "heartbeat timeout — run interrupted by stale recovery",
		}); err != nil {
			// MarkRunTerminal failed — likely the run is not in 'running' status.
			// Don't count it as interrupted; M4-08 adds structured error tracking.
			continue
		}

		report.InterruptedCount++
		report.Details = append(report.Details, info)
	}

	return report, nil
}
```

**Goal:** Add a `TeamWorkspace` interface to `package workspace` that exposes the M3 team-data-domain operations (create team, list teams, snapshot, spawn member, create/update task, list events) as `proto.*` wire types, plus an `AppWorkspace` implementation that adapts each method to the M3-05 `team.Service` (domain types) — defining the boundary the M3-07 API routes + client will proxy across the process boundary.

## Design seam corrections (vs master task doc `04-m3-team-data-domain.md:531-559`)

The master task doc is the approved design intent. The following are **verified implementation decisions**, each backed by cited evidence from the agent-team `3a1a7859` codebase. Every code snippet in this plan is written against the real APIs.

### Seam 1: `app.App` does NOT hold a `team.Service` — inject via `SetTeamService`, leave `app.go` untouched

The master doc (`:535-539`) lists files `team.go` + `app_team.go` + `proto/team.go` — **not `app.go`**. Research confirms why: `app.App` (`internal/app/app.go:55-80`) has fields for Sessions/Messages/History/Permissions/Questions/FileTracker/AgentCoordinator/LSPManager/Skills but **no team field** (grep `team\.|Team|TeamService` over `internal/app/` returns zero hits). `app.New` (`app.go:86-155`) constructs every service from `conn *sql.DB`, and `team.NewService` likewise needs `*sql.DB` + 6 stores — so wiring it into `app.New` is the *natural* home, but doing so is out of M3-06's stated file scope and would make M3-06 touch the highest-blast-radius file in the repo.

**Decision:** `AppWorkspace` gets a private `team team.Service` field (nil-able) + a `SetTeamService(team.Service)` method. Every `TeamWorkspace` method's first line is the `nilService` guard (returns a stable error if the Service was never injected — e.g. in tests that don't exercise team, or before M3-08 wires the flag). This mirrors how `AppWorkspace` already exposes `App()` / `Store()` accessors and how its agent methods guard `if w.app.AgentCoordinator == nil` (`app_workspace.go:102,115,122,...`). The actual Service construction + injection is the M3-08 wiring task (or a one-line `NewAppWorkspace` follow-up) — explicitly scoped out. **Evidence:** `internal/app/app.go:55-155` (no team field), `internal/workspace/app_workspace.go:28-40` (AppWorkspace struct + constructor), `:101-107` (AgentCoordinator nil-guard precedent).

### Seam 2: The `TeamWorkspace` interface method names ALIGN to `team.Service`, not the master doc; `SendTeamMessage` is dropped

The master doc interface (`:543-552`) names 8 methods, but 5 mismatch the real M3-05 `team.Service` interface (`internal/team/service.go:124-147`):

| master doc name | real `team.Service` method | issue |
|---|---|---|
| `CreateTeam` | `CreateTeam` | ✓ match |
| `ListTeams` | `ListTeams` | ✓ match (Service returns `[]Team`, proto wraps in `ListTeamsResponse`) |
| `GetTeamSnapshot` | `GetTeamSnapshot` | ✓ match |
| `SpawnTeamMember` | `SpawnMember` | ✗ rename → `SpawnMember` |
| `CreateTeamTask` | `CreateTask` | ✗ rename → `CreateTask` |

| `ListTeamEventsAfter` | `ListEventsAfter` | ✗ rename → `ListEventsAfter` |

**Decision:** The `TeamWorkspace` interface uses the real Service method names (`SpawnMember`, `CreateTask`, `UpdateTask`, `ListEventsAfter`) so `AppWorkspace`'s implementation is a thin, correct passthrough rather than a rename shim. `SendTeamMessage` is **removed from M3-06 scope** entirely: there is no `team.Service` method to delegate to (the mailbox tables `team_mailbox_messages` / `team_message_receipts` are deferred to M3b per the M3-01 migration comment `:23-25`), so an implementation could only return `ErrNotImplemented` — a dead method on the interface is worse than no method (YAGNI). M3b's mailbox work will add both the Service method and the `TeamWorkspace` method together. The interface thus has **7 methods** (CreateTeam, ListTeams, GetTeamSnapshot, SpawnMember, CreateTask, UpdateTask, ListEventsAfter). **Evidence:** `internal/team/service.go:124-147` (Service interface), `internal/db/migrations/20260614000000_create_team_tables.sql:23-25` (mailbox deferred).

### Seam 3: proto types are a SEPARATE set from domain types — same field shapes, different package, deliberate duplication

The master doc has `TeamWorkspace` return `proto.TeamSnapshot` etc. (wire types), while `team.Service` returns `team.TeamSnapshot` (domain types, M3-03). These are **two type sets** for the same conceptual data, by design: domain (`package team`) carries business semantics (named-string Status enums with `Valid()`, `time.Time`/`*int64`/`*time.Time` for idiomatic Go); proto (`package proto`) is the serialization boundary (plain string/string-pointer fields, JSON tags, no methods) that crosses the HTTP/SSE wire in M3-07. The converters live in `internal/workspace/team.go` (`teamToProto`/`protoToTeam`, etc.) — the same pattern as M3-04's persistence↔domain `convert.go` (`internal/team/convert.go`), just a different axis (domain↔wire instead of domain↔persistence).

**Decision for proto field types:** proto uses the *exact same* Go types as domain for fields that serialize identically — `time.Time` (marshals to RFC3339Nano), `*int64`/`*time.Time` (nullable pointers, `omitempty`), named string types re-declared in proto (`TeamStatus`/`MemberStatus`/`TaskStatus`/`RunStatus` as plain `string`-based types so proto doesn't depend on `package team`). This keeps the converters trivial (field-by-field copy) and the wire format identical to what the domain JSON round-trip tests in M3-03 already lock. proto does **not** depend on `package team` (avoids an import from the wire layer into the domain layer — keeps the dependency direction `workspace → team` + `workspace → proto`, never `proto → team`). **Evidence:** `internal/team/models.go` (M3-03 domain shapes), `internal/proto/requests.go:11-16` (proto plain-struct + json-tag convention), `internal/team/convert.go:17-60` (converter-helper precedent).

### Seam 4: Two response wrappers — `ListTeamsResponse`, `TeamEventsResponse`

The master doc interface returns `proto.ListTeamsResponse` (`:545`) and `proto.TeamEventsResponse` (`:551`) — paginated wrappers, not bare slices. The Service returns bare slices (`[]Team`, `[]TeamEvent`). proto defines the two wrappers as simple structs: `Teams []Team`, `Events []TeamEvent` (no cursor/next-page token yet — YAGNI; M3-07 can add pagination if the wire needs it). This matches the master doc's intent (named response types) without over-engineering.

**Evidence:** master doc `:545,551`; `team.Service.ListTeams`/`ListEventsAfter` return bare slices (`service.go:127,145`).

### Seam 5: Test reuse — export the M3-05 `newServiceFixture` via an internal test helper

M3-06's end-to-end test (acceptance #3: `TeamWorkspace → Service → store`) needs a real `team.Service` over in-memory SQLite. M3-05 already has `newServiceFixture(t) (Service, *sql.DB)` in `internal/team/service_test.go:10-22`, but it's package-scoped (unexported) and lives in `package team`'s test files — `internal/workspace` can't call it directly. **Decision:** add a tiny exported test-helper file `internal/team/testing_workspace.go` (or extend the existing test-helper export pattern) — BUT that changes the M3-05 surface. Cleaner M3-06-scoped option: the workspace test **re-constructs** a Service in-process using the *exported* `team.NewService` + the M3-04 store constructors (all exported: `NewTeamStore`, etc.) over an in-memory SQLite that the workspace test sets up itself (copying the 6-line `newStoreFixture` body — `sql.Open("sqlite", ":memory:")` + `SetMaxOpenConns(1)` + `PRAGMA foreign_keys=ON` + `goose.Up`). This keeps M3-06 fully self-contained (no M3-05 test-file edits) at the cost of ~6 duplicated lines in the test helper. The plan ships a workspace-package `newTeamWorkspaceFixture(t)` helper that builds the DB + stores + Service + `AppWorkspace` + injects the Service, so each test is one line. **Evidence:** `internal/team/store_test_helpers.go:21-40` (`newStoreFixture` body), `internal/team/service_test.go:10-22` (`newServiceFixture`), exported store constructors (verified via `NewTeamStore` etc. in M3-04).

### Seam 6: `ClientWorkspace` does NOT implement `TeamWorkspace` in M3-06

The master doc says only "AppWorkspace implements TeamWorkspace" (acceptance #1, `:557`). `ClientWorkspace` (`internal/workspace/client_workspace.go`) proxies to a remote server via `*client.Client` — its team methods belong to M3-07 (API routes + client SDK), which is where the client-side `TeamWorkspace` impl lands alongside the server routes. M3-06 ships only the interface + the AppWorkspace impl + proto types. The compile-time assertion `var _ TeamWorkspace = (*AppWorkspace)(nil)` (mirroring `var _ Workspace = (*AppWorkspace)(nil)` at `app_workspace.go:420`) is M3-06's acceptance #1 proof. **Evidence:** `internal/workspace/app_workspace.go:420` (existing compile-assert), `internal/workspace/client_workspace.go:31-62` (client delegates to `*client.Client`, no team methods).

// assertTimeRT compares two time.Time by wall-clock equality — JSON marshal
// normalizes to UTC RFC3339Nano and drops the monotonic reading, so a
// reflect.DeepEqual comparison would spuriously fail. (Same semantics as the
// M3-03 domain round-trip tests.)
func assertTimeRT(t *testing.T, want, got time.Time, msg string) {
	t.Helper()
	assert.Truef(t, want.Equal(got), "%s: time round-trip mismatch want=%v got=%v", msg, want, got)
}

func rt(t *testing.T, v any, target any) []byte {
	t.Helper()
	b, err := json.Marshal(v)
	require.NoError(t, err)
	require.NoError(t, json.Unmarshal(b, target))
	return b
}

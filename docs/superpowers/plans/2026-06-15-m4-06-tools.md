## Architecture

### Tool injection seam (Design Seam 3 + 4)

The `TurnRunner` interface must NOT change (10 mock impls across tests). Instead:

```go
// internal/agent/team_call.go — NEW optional interface
type ToolSettableRunner interface {
    SetTools(tools []fantasy.AgentTool)
}

// internal/agent/turn_runner_adapter.go — implement it
func (a *TurnRunnerAdapter) SetTools(tools []fantasy.AgentTool) {
    a.sa.SetTools(tools)
}
```

In `MemberRunner.Start()`, after `factory.BuildRunner`:
```go
if ts, ok := runner.(agent.ToolSettableRunner); ok {
    ts.SetTools(m.memberTools)
}
```

The runner is built once at Start() and reused every turn — tools are set once, at startup. This avoids per-turn overhead and doesn't change the TurnRunner interface.

### TeamReportStatus tool

```go
func NewTeamReportStatusTool(memberID, teamID string, svc Service) fantasy.AgentTool
```

**Parameters:**
| Param | Type | Required | Description |
|---|---|---|---|
| `task_id` | string | yes | The task to update |
| `status` | string | yes | New status (TaskStatus enum) |
| `result_summary` | string | no | Optional result text |

**Handler logic:**
1. Validate status is a valid TaskStatus
2. GetTask to read current task + version
3. **Ownership check**: only allow if `task.AssigneeMemberID == memberID` or if task is unassigned (member self-claims); reject with permission error otherwise
4. Call `svc.UpdateTask` (read-then-CAS, single attempt per Service.UpdateTask)
5. On `ErrVersionConflict`: retry ONCE more (read again + CAS)
6. If second attempt also conflicts: log warn, return error "Task was modified concurrently. Your update could not be applied. Transition to blocked."
7. On success: return task status + acknowledgement

**CAS retry rationale:** The Service.UpdateTask already does read-then-CAS internally. We wrap with ONE retry at the tool level. Two attempts total. If both fail, the member should know it's blocked, not silently fail.

### TeamSendMessage tool

```go
func NewTeamSendMessageTool(memberID, teamID, role string, svc Service) fantasy.AgentTool
```

**Parameters:**
| Param | Type | Required | Description |
|---|---|---|---|
| `recipient_type` | string | yes | direct, broadcast, or role |
| `to_member_id` | string | if direct | Target member ID |
| `to_role` | string | if role | Target role |
| `kind` | string | yes | message or task_status only |
| `summary` | string | yes | Short summary |
| `payload` | string | yes | Message body |

**Handler logic:**
1. Validate `kind`: reject `shutdown_request` / `shutdown_ack` (member cannot shutdown others)
2. Validate `recipient_type`: must be valid RecipientType
3. Call `svc.SendMessage` with from_member_id set to this member
4. Return success + resolved recipient IDs

**Actor policy:**
- kind = `shutdown_request` / `shutdown_ack`: **DENIED** (only leader can shut down)
- kind = `message` / `task_status`: **ALLOWED**

## Design seams

1. **Tools as closures**: Each tool captures memberID/teamID/role at construction time. The tool handler always knows "who am I" without reading it from context/actor. This avoids the complexity of threading ActorContext through the full agent pipeline (SessionAgent.Run sets tools.SessionIDContextKey but not ActorContext).

2. **CAS retry**: Service.UpdateTask already does read-then-CAS internally. The tool wraps with ONE additional retry. This is deliberately not a retry loop — after two attempts, the member should know it's blocked so the leader can resolve.

3. **Tool injection via optional interface**: `ToolSettableRunner` is a separate interface from `TurnRunner`. TurnRunnerAdapter implements it; mocks don't have to. MemberRunner checks at startup; if the runner doesn't support it, tools simply aren't set (handled gracefully).

4. **No modifications to M1/M2 code**: Only `turn_runner_adapter.go` gets a NEW method (not interface change). `team_call.go` gets a NEW interface alongside TurnRunner. Existing mocks and tests are unaffected.

# M5.4 — Member Permission Popup: Always-Show + Queue Design

> Status: design (pre-implementation)
> Parent milestone: M5 Team UI Visibility
> Supersedes the M5.2 "active-session-only popup" compromise.

## Problem

M5.2 shipped a compromise: member permission popups only appear when the user is
viewing that member's session. When focused elsewhere, `PermissionBridge.Request`
hits the `IsActiveSession` gate and falls through to the `SkipRequests` gate —
which is `false` in normal mode — so the member's tool call is **silently
denied**. The user never sees a popup; the member appears stuck. This is the
"member gets blocked" failure we are fixing.

A second, latent failure: even when popups do appear, two concurrent member
requests race. `openPermissionsDialog` does `CloseDialog` then `OpenDialog` with
a fixed `PermissionsID`, so a second request's dialog overwrites an undecided
first one. The first member then blocks until a 60s timeout deny — silent again.

## Goals

1. **Always show.** Any team-member permission request produces a popup
   regardless of which session is focused, with the source (team/member/tool)
   clearly marked. Members are never silently denied for lack of a popup.
2. **Sequential queue.** Concurrent member requests are presented one at a time
   (FIFO). Deciding one advances to the next. No request overwrites another.
3. **Fair timeout.** A request's 60s countdown starts when it becomes the
   *displayed* slot, not when it is enqueued — a request never times out before
   the user has seen it.
4. **Upgradeable.** The queue architecture must support a later 方案③ upgrade
   (visible "N waiting" indicator) without rework.

## Non-goals

- Visible queue-depth indicator (方案③). Designed-for, not built.
- Wiring audit events to the DB (still deferred, per prior decision).
- Changing leader flow (`hasTeam=false` delegates to inner — untouched).
- Removing the `SkipRequests` (yolo) gate — kept, before `requestWithUI`.

## Confirmed decisions

- Focus stealing is acceptable. Popups appear over whatever session is focused.
- Timeout: 60s (was 30s). `defaultRequestTimeout` const updated.
- Timer starts at display (Option A), not at enqueue.
- Multi-member concurrency is a core problem; 方案② (one-at-a-time queue) now,
  方案③ (queue + visibility) later.

## Architecture

### Bridge-side queue (source of truth)

All display coordination lives in the bridge. The TUI stays simple: it renders
whatever single request the bridge publishes. The existing FSM `PermissionQueue`
(used for expiry bookkeeping) is left untouched to keep blast radius minimal.

New bridge state, guarded by a single `queueMu`:

```go
type pendingEntry struct {
    reqID     string
    ch        chan bool                  // decision from UI (buffered, size 1)
    tctx      *TeamPermissionContext
    opts      permission.CreatePermissionRequest
    ac        actor.ActorContext
    timeoutCh chan struct{}              // closed when display-timer fires
    timer     *time.Timer                // nil until promoted to displayed
}
```

Bridge fields:

```go
displayFIFO []*pendingEntry             // waiting, not yet shown
displayed   *pendingEntry               // the one currently shown (≤1 invariant)
entries     map[string]*pendingEntry    // reqID → entry, O(1) resolve/cancel/timeout
```

**Invariant:** at most one entry is `displayed` at a time. Only the `displayed`
entry has been `Publish`'d to the UI broker and has a live timer. Waiting entries
have neither.

### `Request` flow (replaces the current branch at lines ~297-309)

After the grant check:

```go
// Team session (hasTeam && TeamID && MemberID) — always show a popup,
// regardless of focused session.
if b.inner.SkipRequests() {
    // yolo — auto-allow, bypass UI. Kept behavior.
    return true, nil
}
return b.requestWithUI(ctx, opts, ac)
```

The `IsActiveSession` check is removed entirely. `ActiveSessionTracker` stays
(tracing, future use) but is no longer a gate.

### `requestWithUI`

1. Build `pendingEntry` (reqID, ch, tctx from `ac`, opts, ac).
2. Under `queueMu`: append to `displayFIFO`, insert into `entries`, and
   *also* retain `pendingRequests[reqID] = ch` + `teamContexts[reqID] = tctx`
   (the existing maps the TUI/`ResolveRequest` use today — kept so the TUI's
   `TeamContextFor(perm.ID)` lookup still works on the displayed entry).
3. `pumpDisplay()` (handles starting the timer + Publish).
4. `select { <-ctx.Done() | <-entry.timeoutCh | allowed := <-entry.ch }`.
5. On terminal: remove from `entries`, `pendingRequests`, `teamContexts`,
   `displayFIFO`; return (`ctx.Err()` / `false` / `allowed`).

### `pumpDisplay()` — the only path to the UI

Under `queueMu`: if `displayed != nil`, return. Else pop `displayFIFO` front →
set `displayed` → arm `timer = time.AfterFunc(b.requestTimeout, handleTimeout(reqID))`.
**Outside** the lock: `b.inner.Publish(...)` so the TUI opens the dialog. Trace
log `perm_bridge: pumpDisplay published` with reqID + FIFO depth after.

### Terminal handlers — single ownership model

Exactly one of three drivers terminates an entry. All three use the **same**
lock+membership-token dance, so concurrent drivers (e.g. timeout racing cancel)
are safe and idempotent:

```
acquire queueMu
entry, ok := entries[reqID]
if !ok { release lock; return /* already handled, no-op */ }
wasDisplayed := (b.displayed == entry)
if wasDisplayed { b.displayed = nil }
remove reqID from entries, pendingRequests, teamContexts; splice out of displayFIFO
release lock
if wasDisplayed { pumpDisplay() }   // acquires its own lock
signal the blocking goroutine       // feed ch OR close timeoutCh OR nothing for ctx
```

`entries[reqID]` membership is the single "who wins" token: the first driver to
grab the lock and find the entry present owns termination; later drivers find it
gone and no-op. The blocking `requestWithUI` goroutine does **no** cleanup of its
own — it only observes which of its three select arms fired and returns the
corresponding value (`allowed` / `false` / `ctx.Err()`).

- **`ResolveRequest(reqID, allowed, scope)`** runs the dance; then feeds
  `entry.ch <- allowed` (buffered, size 1, so it never blocks even if the
  goroutine has already exited on another arm — the channel is GC'd with the
  entry). Returns the existing "not pending" error when `!ok`.
- **`handleTimeout(reqID)`** is the `time.AfterFunc` callback for the displayed
  entry. Runs the dance; then closes `entry.timeoutCh` (wakes the goroutine →
  returns `false, nil`). When `!ok`, no-op (resolved/cancelled first).
- **`ctx.Done()` arm:** the `requestWithUI` goroutine itself runs the dance for
  `entry`; then returns `false, ctx.Err()`. (The goroutine is the driver here.)

`pumpDisplay()` always acquires `queueMu` itself; callers must release the lock
before calling it (never call it while holding `queueMu`).

### UI side (方案②)

Essentially unchanged. Because the bridge now publishes one request at a time,
the existing `openPermissionsDialog` (CloseDialog + OpenDialog) sequences
correctly — no two team permission dialogs coexist. Source marking already
works via `TeamPermissionContext` → `NewTeamPermissionDialog`. The team dialog
already shows team/member/role/tool/action/resource.

### 方案③ upgrade path

The queue already holds all waiting entries. The upgrade is purely additive:
add `func (b *PermissionBridge) PendingCount() int` (returns
`len(displayFIFO) + bool(displayed!=nil)` under a read lock). The TUI renders an
"N waiting" badge on the permissions dialog / status line. No change to the
queue mechanics, no change to terminal handlers. This is explicitly out of scope
for this spec but the design must not block it.

## Data flow (member write, focused on leader session)

1. Member's `write` tool → `PermissionBridge.Request` with team actor context.
2. `hasTeam=true` → grant miss → `SkipRequests=false` → `requestWithUI`.
3. Entry enqueued. `pumpDisplay`: FIFO empty → promote to `displayed` → Publish.
4. TUI receives pubsub event → `openPermissionsDialog` → `TeamContextFor` hit →
   team dialog (source marked) opens over the leader's view (focus steal OK).
5. User clicks Allow-for-Task → `PermBridgeResolve` → `ResolveRequest`.
6. `displayed` cleared → `pumpDisplay` → (if FIFO non-empty) next request's
   Publish → its dialog opens. First member's `Request` returns `true`.

## Error handling

- **Timeout (60s, displayed):** deny, advance queue.
- **Context cancel (member run cancelled):** remove entry, advance queue if it
  was displayed, return `ctx.Err()`.
- **Late resolve (entry already timed out/cancelled):** `ResolveRequest` returns
  "not pending" error; UI caller already closed its dialog via the terminal
  path. No panic, no blocked channel.
- **Late timeout (entry already resolved):** `handleTimeout` no-ops on the
  `displayed != entry` check.

## Testing

Unit tests in `internal/team/permission_bridge_test.go`:

1. **Always-show:** team request with tracker pointing at a *different* member
   still routes to `requestWithUI` (resolves via `ResolveRequest`). Replaces the
   implicit "active-session" expectation in the existing context test.
2. **Sequential queue:** enqueue two requests concurrently; assert only the first
   is `TeamContextFor`-visible until resolved; after resolving the first, the
   second becomes visible; both resolve correctly.
3. **Fair timeout:** two queued requests; first unresolved; advance the bridge's
   requestTimeout; assert the *first* (displayed) times out, the *second* does
   not time out while waiting (no timer armed on it). Then resolve the second.
4. **Timeout advances queue:** displayed timeout → next request promoted.
5. **Context cancel removes + advances:** cancel a displayed request's ctx →
   queue advances.
6. **Late resolve no-op:** resolve after timeout → error, no panic.
7. Existing tests updated: `StoresAndClearsTeamContext`, `TimeoutDeniesAndCleansUp`,
   `CtxCancelDeniesAndCleansUp`, `TraceLogging` — adjust setup (no longer need
   tracker-matching since the gate is gone; keep tracker where it aids tracing).
8. Trace logging: add `pumpDisplay` published line; assert it appears for the
   first request and not for a still-waiting second.

Constraints (CLAUDE.md): tests `-count=3` not `-race`; `go build` authoritative;
single-line conventional commit no trailer; one commit per task.

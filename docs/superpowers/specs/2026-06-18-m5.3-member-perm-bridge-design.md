# M5.3 — Member Permission Bridge: Wire Up the Broken Ends

**Date:** 2026-06-18
**Status:** Design
**Predecessors:** M5.1 (member tool loop fix), M5.2 (PermissionBridge + ActiveSessionTracker wiring)
**Branch target:** `agent-team`

## Problem

M5.2 built the `PermissionBridge` to route team-member tool calls through a UI
approval flow instead of auto-denying. The bridge's intended data flow is:

```
member tool call
  → PermissionBridge.Request (team session detected via ActorContext)
  → requestWithUI: store reqID→ch in bridge.pendingRequests, Enqueue to queue,
       Publish(CreatedEvent) to inner broker so the TUI opens a dialog
  → BLOCK on <-ch
  → (later) UI calls ResolveRequest(reqID, allowed) → feeds ch
  → member receives the boolean, continues/stops
```

This flow is **broken at both ends**:

1. **TUI never sets `teamCtx` on the dialog.** `openPermissionsDialog`
   (`internal/ui/model/ui.go:3636`) always uses `dialog.NewPermissions`, which
   leaves `teamCtx == nil`. `teamCtx` is only ever set by `NewTeamPermissionDialog`,
   which is exclusively used in tests. Because `teamCtx` is nil, the dialog's
   button dispatch (`ui.go:1628-1639`) routes to `PermissionGrant/Deny` →
   `inner.Grant/Deny` → `inner.resolve()` looks up `inner.pendingRequests[reqID]`,
   which was never created (the bridge only `Publish`es; it never calls
   `inner.Request`). So the user's button press is a silent no-op.

2. **Nothing ever feeds `ch`.** The bridge blocks on `<-ch`. `ResolveRequest` is
   the only feeder, and (per #1) it is never called. The queue's 5-minute expiry
   calls `fsm.Expire`, which only mutates the store status + emits audit — it does
   not touch `ch`. So `requestWithUI` blocks until `ctx.Done()`, at which point the
   member effectively experiences "permission denied."

Net effect: **the member is still denied even after the M5.2 wiring.** The bridge
is a dead-end: publish out, block forever, never resolve.

### Secondary problem (timeout)

Even after wiring #1/#2, the queue's expiry path does not feed `ch`. A member
whose request the user simply ignores would block until `ctx.Done()` (possibly
the whole run), not until a clean 30s timeout.

## Goals

- Make the member permission bridge actually round-trip: member asks → dialog
  opens with team context → user decides → member receives the decision.
- Ensure a clean timeout-denial path so an ignored request does not hang the run.
- Do this without polluting `permission.PermissionRequest` (the inner service's
  core type) with team concepts.

## Non-Goals (YAGNI)

- No changes to `permission.PermissionRequest` struct.
- No changes to `permission_queue.go` / `fsm.Expire` semantics (store/audit only).
- No changes to the leader permission path (already works via `inner.Request`).
- No full task/session-scope grant persistence — `scope` is passed through and
  the in-memory `GrantStore` already exists; deeper grant lifecycle is a later task.

## Design

### Decision: A3 — bridge-side team context map (not on PermissionRequest)

`permission.PermissionRequest` is the inner service's core type, shared across
`Request`/`Grant`/`Deny`/pubsub and potentially DB serialization. Embedding a
team concept there would make a team-agnostic package depend on team semantics.
Instead, the bridge — which already holds all team state (`pendingRequests`,
`queue`, `grantStore`) — also holds a `reqID → TeamPermissionContext` map. The
TUI queries it when building the dialog. Same layer, no cross-layer leak.

### Decision: B1 — move `TeamPermissionContext` down to the `team` package

Today `TeamPermissionContext` is defined in `internal/ui/dialog` (UI layer). The
bridge lives in `internal/team` (domain layer). If the bridge constructs it, that
would create `team → dialog` (domain → UI), an inverted dependency.

`TeamPermissionContext`'s fields (TeamName, MemberName, MemberRole, TaskTitle)
are team domain data. Move the struct definition into `internal/team` (new file
`internal/team/permission_types.go`). `dialog` imports `team` to use the type —
`dialog → team`, correct layering direction. Pure-render helpers
(`TeamPermissionButton`, `BuildTeamHeaderLines`, `DefaultTeamButtons`) stay in
`dialog`.

### Lifecycle & timeout (secondary fix)

The queue's `fsm.Expire` (5 min) is general-purpose store/audit and stays as-is.
The bridge owns the `ch` lifecycle directly via a **bridge-local `time.AfterFunc`**
in `requestWithUI`, decoupled from the queue:

```
expiry := 30s  (matches PermissionRequest.ExpiresAt already set)
timer := time.AfterFunc(expiry, func() {
    pendingMu.Lock()
    if ch, ok := b.pendingRequests[reqID]; ok {
        delete(b.pendingRequests, reqID)
        delete(b.teamContexts, reqID)
        ch <- false   // timeout = denial
    }
    pendingMu.Unlock()
    b.queue.Dequeue(reqID)
})

select {
case <-ctx.Done():
    timer.Stop()
    cleanup(reqID)  // delete pendingRequests + teamContexts
    b.queue.Dequeue(reqID)
    return false, ctx.Err()
case allowed := <-ch:
    timer.Stop()
    b.queue.Dequeue(reqID)  // teamContexts already cleared by feeder
    return allowed, nil
}
```

Both the timeout callback and `ResolveRequest` delete from `pendingRequests`
**before** feeding `ch` (under the lock), so whichever runs first wins; the other
finds the entry gone and no-ops. This makes `ResolveRequest`'s existing
`request not pending` error path the correct "lost the race" outcome, and
`PermBridgeResolve` already treats it as non-fatal (`ui.go:1629` is `_ = ...`).

### Data flow (after fix)

```
member tool call
  → PermissionBridge.Request (team session, active session matches)
  → requestWithUI:
      store reqID→ch + reqID→TeamPermissionContext
      Enqueue (queue 5min store timer)
      start bridge-local 30s timer
      Publish(CreatedEvent, {ID:reqID, ...})
      block <-ch
  → TUI: pubsub.Event → openPermissionsDialog
      PermBridge().TeamContextFor(reqID) → hit → NewTeamPermissionDialog (teamCtx set)
  → user presses Allow Once → PermissionAllowOnce
      → PermBridgeResolve(reqID, true, "call")
      → ResolveRequest: feed ch<-true, clear maps
  → member's <-ch returns true → continues

(timeout path: 30s timer fires → ch<-false → member receives false → denied cleanly)
```

## Testing

### Unit — `internal/team` (bridge)

- `Request` for an active team session calls `requestWithUI`; `teamContexts[reqID]`
  is populated and `inner.Publish(CreatedEvent, ...)` invoked (assert via a fake
  inner or by subscribing to `inner.Subscribe`).
- `TeamContextFor(reqID)` returns the stored context / `false` when absent.
- `ResolveRequest(allow)` → `ch` receives `true`; both maps cleared after.
- `ResolveRequest(deny)` → `ch` receives `false`; both maps cleared.
- Timeout (inject short TTL) → `ch` receives `false`; maps cleared; queue dequeued.
- `ctx.Done()` → returns `false, ctx.Err()`; maps cleared; queue dequeued.
- Race: timeout fires then user resolves → user's `ResolveRequest` returns
  `request not pending` (no double-feed, no panic).

### Unit — `internal/ui/dialog`

- `NewTeamPermissionDialog` with a `team.TeamPermissionContext` sets `teamCtx`;
  button set is the team three-button set. (Existing tests adapt to the relocated
  type.)

### Integration (light)

- Existing team test fixture: drive leader→member→tool→ and assert at the bridge
  layer (mock or real inner) that the round-trip completes and the member
  continues. If too heavy, stop at the bridge-layer unit above.

# M4.5b: Message Wake & Session Gap Fixes — Design Spec

> Date: 2026-06-16 | Status: draft | Scope: 3 gap fixes

## Background

M4.5 leader tools let the coder agent create teams, spawn members, and send messages. Testing revealed the message pipeline is broken at two points:

```
Leader sends message → DB insert → 🔴 Gap 1: no wake
Member wake → handleWake → 🔴 Gap 2: sessionID is empty → Run fails
```

## Gap Analysis

### Gap 1: No wake after SendMessage

`Service.SendMessage` writes message + receipts to DB, returns recipient IDs. It does NOT wake MemberRunners — only `TeamRunner` holds the member registry needed to call `Wake()`.

**Fix**: Add `WakeMember` to `TeamRunner` interface. Pass `TeamRunner` to `NewLeaderSendMessageTool`. After `svc.SendMessage`, call `runner.WakeMember(ctx, teamID, recipientID, WakeSourceMailbox)` for each recipient.

### Gap 2: Member has no session ID

`TeamRunner.SpawnMember` creates a member via `svc.SpawnMember` (DB record, no session_id). Then `MemberRunner.Start()` loads the DB record, finds `SessionID == nil`, leaves `m.sessionID = ""`.

Later `handleWake` calls `runner.Run(ctx, TeamAgentCall{SessionID: ""})` → `TurnRunnerAdapter.Run` → `SessionAgent.Run` → line 166: `if call.SessionID == "" { return nil, ErrSessionMissing }`.

**Fix**: In `MemberRunner.Start()`, when `dbMember.SessionID` is nil, create a new session via `svc.CreateSession`. Store the session ID on the member record. Use `RecoverMemberSession` (M4-10) to link the session.

But `MemberRunner` only has `Service` — does `Service` have a `CreateSession` method? No. `Service` is the team domain service, not the session service.

Alternative: `TeamRunner.SpawnMember` should create a session BEFORE building the MemberRunner. `TeamRunner` has access to `Service` but not the session service.

Simplest fix: Don't fight the abstraction. In `MemberRunner.Start()`, if `sessionID` is empty, call `svc.StartRun` with an empty session (which already works — see line 275-279, `StartRunRequest{SessionID: m.sessionID}` with empty session). Then the `TurnRunnerAdapter` should create a session on demand if none exists.

Actually, the real fix: `CoordinatorAgentFactory.BuildRunner` should handle session creation. OR: `MemberRunner.handleWake` should create a session on first run.

**Recommended fix**: In `MemberRunner.Start()`, if no session ID exists, generate one and persist it. The `Service` interface doesn't have session management, so we store it locally. The `SessionAgent.Run` checks `SessionID == ""` — we need a real session ID.

Looking at the coordinator's `BuildSessionAgent`: it creates a `SessionAgent` that runs against sessions managed by the coordinator's session service. The `TurnRunnerAdapter` just wraps this. So the SessionAgent needs a valid session ID from the coordinator's session system.

The cleanest approach: **Create a session in `TeamRunner.SpawnMember` before starting the MemberRunner**, using the coordinator's session management. But TeamRunner doesn't have session creation capability.

Simplest working approach: **Generate UUID as session ID in `MemberRunner.Start()` when none exists**. The SessionAgent just needs a non-empty string — it will create a new session internally when Run is called.

It just checks for empty. If we provide any non-empty string, it proceeds. The session service in the coordinator handles creating/finding sessions. Let me check what happens with a UUID that doesn't exist in the session DB.

But `MemberRunner` doesn't go through the coordinator's `Run`. It goes through `TurnRunnerAdapter.Run` → `SessionAgent.Run`. The SessionAgent.Run expects the session to exist (it loads the session from the session service).

So we need to create a real session. The session service is:

`MemberRunner` doesn't have access to `session.Service`. Only the `AgentFactory` or the `TeamRunner` (via the coordinator) has it.

**Final recommendation**: Add session creation to the `AgentFactory` interface. The factory creates a session, builds the SessionAgent, and links them. This is the right seam.

Actually, simpler: `CoordinatorAgentFactory.BuildRunner` already has access to the coordinator. The coordinator has a `BuildSessionAgent` method. We can also create a session via the coordinator's sessions service... but the coordinator doesn't expose session creation in its interface.

OK, simplest working fix: **In `TeamRunner.SpawnMember`, create a session before starting the MemberRunner**. The `TeamRunner` is wired with `Service` + `AgentFactory`. The factory doesn't expose session creation. 

Let me check if we can just use `uuid.New().String()` as the session ID. The SessionAgent.Run will check `call.SessionID == ""` and return ErrSessionMissing. But what happens after the empty check passes? Let me look at what SessionAgent.Run does after the session check.

Actually, looking more carefully at sessionAgent.Run (agent.go:162+), after the empty check, it proceeds to run the fantasy loop. The session ID is used for:

2. Queue management  
3. Passing to the fantasy engine

The fantasy engine then uses the session ID to load the session from the session service. If the session doesn't exist in the session store, the fantasy engine will fail.

So we DO need a real session created. The question is where.

Let me take the simplest approach that works end-to-end:
- `TeamRunner.SpawnMember` creates a session via `svc` ... but `team.Service` doesn't have session creation.

OK, I think the right approach is to give `TeamRunner` a way to create sessions. Let me add a `SessionCreator` interface:

```go
    CreateSession(ctx context.Context, name string) (sessionID string, err error)

```

And pass it to `TeamRunner` at construction time. Then `SpawnMember` creates a session and passes it to the member.

## Design

### Fix 1: TeamRunner.WakeMember + leader tool wiring

**TeamRunner interface** — add:
```go
WakeMember(ctx context.Context, teamID, memberID string, source WakeSource) error
```

**teamRunner implementation** — lookup member by ID, call `mr.Wake(source)`.

**NewLeaderSendMessageTool** — change signature to also take `runner TeamRunner`. After `svc.SendMessage`, call `runner.WakeMember` for each recipient.

### Fix 2: Member session creation

Three options:

**A. TeamRunner creates session in SpawnMember**
- Pass a `SessionCreator` func to TeamRunner
- SpawnMember creates session, stores on member record, sets on MemberRunner
- Most correct, new interface

**B. MemberRunner creates session on first run**
- In `handleWake`, if `sessionID == ""`, call a session creator func
- MemberRunner needs a `createSession func(context.Context) (string, error)` field
- Simpler, self-contained in member lifecycle

**C. AgentFactory creates session in BuildRunner**
- `CoordinatorAgentFactory` already has coordinator access
- `BuildRunner` creates a session via coordinator's session service
- Clean but requires coordinator interface change

**Recommendation: B** — simplest, keeps session creation in the member lifecycle where it belongs. The `TeamRunner.SpawnMember` can set a `createSession` function on the MemberRunner.
